1. PROJECT OVERVIEW & BUSINESS PURPOSE
================================================================================
Marg ERP CRM is a specialized Enterprise Lead Management, Customer Support, and 
Sales Pipeline System designed for Marg ERP software distributors, dealers, and IT 
service providers. 

The application streamlines the entire client lifecycle—from initial lead capture 
via marketing channels to product demonstration, quotation submission, payment 
reconciliation, software installation, customer staff training, ongoing support ticket 
resolution, and annual software license renewals (AMC).

Key System Objectives:
- Track sales opportunities across a 7-stage visual Kanban pipeline.
- Manage sales agent follow-ups with automated SMS & Email reminders.
- Provide a responsive customer support helpdesk for technical issues.
- Maintain an active directory of legacy & running client accounts (28 data attributes).
- Track hardware/software installations and multi-hour staff training sessions.
- Monitor license expiry dates and automate renewal fee collections.

3. END-TO-END BUSINESS PROCESS WORKFLOWS
================================================================================

--------------------------------------------------------------------------------
3.1 PROCESS 1: LEAD GENERATION TO DEAL CLOSED (SALES & ONBOARDING)
--------------------------------------------------------------------------------
Goal: Convert an raw inquiry into a paying, fully installed, trained Marg ERP client.

Step 1: Lead Capture & Registration
- Source: Web form, Google Ads, Exhibition, Cold Call, or Bulk Excel Import.
- Record Created: Entry inserted into `leads` table with ID `LD-XXXX` and status `new`.
- Auto-Assignment: System or Manager assigns lead to a Sales Executive (e.g., Amit Sen).
- Audit: Timeline entry logged ("Lead auto-assigned to Amit Sen").

Step 2: Initial Discovery & Follow-up
- Sales Executive logs in, views pending follow-up on Dashboard.
- Executive calls prospect to understand business requirements (Pharmacy, Retail, FMCG).
- Executive logs call result in `followups` table and adds timeline remark.
- Lead status updated from `new` to `contacted`.

Step 3: Product Demonstration
- Executive schedules demo (`demos` table, ID `DM-XXXX`).
- Engineer conducts live demo (Online or On-site).
- Engineer records client rating (1-5) and feedback ("Requires batch billing").
- Lead status updated to `interested` / `demo_completed`.

Step 4: Quotation & Proposal Submission
- Executive creates formal quote (`quotations` table, ID `QT-XXXX`).
- System calculates Taxable Amount + 18% GST = Grand Total.
- Quotation PDF sent to prospect via Email/WhatsApp link.
- Lead status updated to `quotation_sent`.

Step 5: Deal Closure & Payment Collection
- Prospect approves proposal. Executive creates Invoice (`invoices` table, ID `INV-XXXX`).
- Client pays advance/full payment. Receipt recorded in system.
- Lead status updated to `payment_pending` or `payment_received`.

Step 6: Installation & Deployment
- System automatically generates Installation Order (`installations` table, ID `INS-XXXX`).
- Assigned Field Engineer visits client site, verifies hardware, sets up Marg DB, 
  completes 5-point checklist.
- Installation status marked `completed`. Lead status updated to `install_pending` -> `installed`.

Step 7: Staff Training & Certification
- System generates Training Record (`trainings` table, ID `TRN-501`).
- Trainer conducts 6 hours of user training on billing, inventory, and GST returns.
- Logged hours updated to 6/6. Status marked `certified`.
- Lead status updated to `won` (Active Client).

Step 8: Master Directory Transition & Renewal Tracking
- Lead profile is archived into `client_directory` master records.
- License Renewal entry created (`renewals` table) with expiry date 1 year from activation.

--------------------------------------------------------------------------------
3.2 PROCESS 2: TICKET OPEN TO TICKET CLOSED (CUSTOMER SUPPORT HELPDESK)
--------------------------------------------------------------------------------
Goal: Efficiently resolve technical customer queries and system errors.

Step 1: Ticket Creation
- Client calls support or submits issue online.
- Support Executive opens `modules/support.php` and clicks "New Ticket".
- Fields filled: Customer Name, Phone, Email, Product, Priority (Critical/High/Medium/Low), 
  Problem Description, Due Date.
- Ticket created in `support_tickets` table with ID `TCK-XXXX` and status `open`.

Step 2: SLA & Engineer Assignment
- System notifies assigned Support Technician (e.g., Rahul P.).
- Technician accepts ticket. Status changes to `in_progress`.

Step 3: Technical Troubleshooting
- Technician establishes remote session (AnyDesk / TeamViewer) or visits site.
- Troubleshoots database connection, printer setup, or license key configuration.
- Adds work notes and progress updates to ticket custom fields / logs.

Step 4: Resolution & Verification
- Issue is tested and verified with customer.
- Technician updates ticket status to `resolved` and inputs Resolution Summary.

Step 5: Quality Check & Closure
- Support Manager or automated trigger verifies customer satisfaction.
- Ticket status updated to `closed`. Customer receives SMS confirmation.

--------------------------------------------------------------------------------
3.3 PROCESS 3: PRODUCT DEMONSTRATIONS & DEPLOYMENT WORKFLOW
--------------------------------------------------------------------------------
1. Entry created in `demos` linked to `lead_id`.
2. Engineer assigned (`engineer` column).
3. Notification sent to engineer with client address/contact.
4. Demo executed -> Feedback & rating logged -> Lead priority auto-adjusted (Hot if Rating >= 4).

--------------------------------------------------------------------------------
3.4 PROCESS 4: QUOTATION & INVOICE PAYMENT COLLECTION WORKFLOW
--------------------------------------------------------------------------------
1. Quotation generated with itemized pricing + GST.
2. Link generated for client view.
3. Upon approval, convert Quotation to Invoice with 1 click.
4. Outstanding balance tracked in real-time (`balance_amount = total_amount - paid_amount`).
5. Overdue payment alerts sent to Sales Executive after due date.

--------------------------------------------------------------------------------
3.5 PROCESS 5: SOFTWARE INSTALLATION & USER TRAINING WORKFLOW
--------------------------------------------------------------------------------
1. Installation task created (`installations` table).
2. Checklist items: 
   - [x] Operating System & Hardware Check
   - [x] Marg ERP Software Installation
   - [x] Database Configuration & Path Setup
   - [x] Thermal/Laser Printer Driver Setup
   - [x] LAN Multi-user Data Sharing Config
3. Training scheduled (`trainings` table) for 6 cumulative hours.
4. Certificate generated once `logged_hours` == `total_hours`.

--------------------------------------------------------------------------------
3.6 PROCESS 6: AMC RENEWAL & CLIENT DIRECTORY MANAGEMENT
--------------------------------------------------------------------------------
1. Client Directory maintains running software details, version, and license trade.
2. Background cron (`cron_scheduler.php`) scans `renewals` table daily.
3. If `expiry_date` is within 30 days, status set to `grace` and renewal SMS/Email fired.
4. When renewal fee paid, `expiry_date` extended by 365 days and status reset to `active`.

4. MOBILE APP ARCHITECTURE & MYSQL DATABASE CONNECTIVITY GUIDE
================================================================================

--------------------------------------------------------------------------------
4.1 CRITICAL TECHNICAL WARNING: WHY DIRECT MYSQL TO APK IS NOT PERMITTED
--------------------------------------------------------------------------------
When building an Android `.APK` using Bolt.ai, React Native, Flutter, or Java/Kotlin, 
YOU MUST NEVER ATTEMPT DIRECT MYSQL CONNECTION (e.g., connecting directly to port 
3306 or 3307 from the mobile phone code).

Reasons why direct MySQL connection from APK fails in real-world deployment:
1. EXTREME SECURITY HAZARD:
   Direct MySQL connection requires embedding database credentials (`DB_USER`, `DB_PASS`, 
   `DB_HOST`) inside the mobile app binary. Anyone can decompile an `.APK` file in 30 
   seconds using free tools (like JADX or apktool) to extract raw database credentials, 
   giving attackers full read/write/delete access to your MySQL server!
2. NETWORK BLOCKING & FIREWALLS:
   Mobile devices operate on cellular networks (4G/5G/WiFi) with changing IP addresses. 
   Database servers explicitly block public MySQL port access (3306/3307) for security.
3. CONNECTION TIMEOUTS & POOL EXHAUSTION:
   Mobile networks disconnect frequently. Direct TCP MySQL sockets break on app sleep, 
   causing app crashes and exhausting MySQL's max connection limits within minutes.

--------------------------------------------------------------------------------
4.2 RECOMMENDED ARCHITECTURE: SECURE REST API INTERFACE (HTTPS JSON)
--------------------------------------------------------------------------------
The industry-standard, secure architecture for connecting an APK to a MySQL database 
is a 3-Tier Architecture using a PHP REST API middleware:

  +-----------------------+              +-----------------------+              +-----------------------+
  |    MOBILE APP (APK)   |  HTTPS JSON  |   PHP WEB BACKEND     |  PDO Socket  |    MYSQL DATABASE     |
  | (React Native/Flutter)| <----------> | (c:/xampp/htdocs/...) | <----------> |      (marg_crm)       |
  |  Built by Bolt.ai     |   REST API   | Security & Validation |  Port 3307   | Local / Server DB     |
  +-----------------------+              +-----------------------+              +-----------------------+

How It Works:
1. The Mobile App (APK) makes HTTPS requests (`GET`, `POST`, `PUT`) to API endpoints on 
   your server (e.g., `https://your-domain.com/api/leads.php`).
2. The PHP API checks user authentication via a Secure Token (JWT or API Token header).
3. The PHP script sanitizes input, executes PDO prepared statements against MySQL safely, 
   and returns clean JSON data back to the mobile app.
4. The Mobile App parses JSON and renders beautiful native UI cards, tables, and lists.

--------------------------------------------------------------------------------
4.3 ALTERNATIVE ARCHITECTURE: PWA / WEBVIEW HYBRID APK
--------------------------------------------------------------------------------
If you want instant deployment without rebuilding API logic:
1. Host the Marg ERP CRM web app on a public SSL web server (`https://crm.yourcompany.com`).
2. Use Bolt.ai or Android Studio to generate a Trusted Web Activity (TWA) or Android 
   WebView wrapper APK.
3. The APK acts as a native app shell displaying the responsive web system with full 
   mobile hardware capabilities (Camera for document scanning, Push Notifications,

    - `updated_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

11. TABLE: `renewals`
    - `id` VARCHAR(20) PRIMARY KEY (e.g. 'RNW-902')
    - `lead_id` VARCHAR(20) NOT NULL (FK -> leads.id)
    - `customer_name` VARCHAR(100) NOT NULL
    - `product_name` VARCHAR(100) NOT NULL
    - `expiry_date` DATE NOT NULL
    - `days_remaining` INT NOT NULL
    - `renewal_fee` DECIMAL(12,2) NOT NULL
    - `status` VARCHAR(20) DEFAULT 'active' (active, grace, expired)
    - `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP

12. TABLE: `timeline`
    - `id` INT AUTO_INCREMENT PRIMARY KEY
    - `lead_id` VARCHAR(20) NOT NULL (FK -> leads.id)
    - `log_time` TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    - `actor` VARCHAR(100) NOT NULL
    - `action_taken` TEXT NOT NULL

13. TABLE: `notifications`
    - `id` INT AUTO_INCREMENT PRIMARY KEY
    - `user_id` INT NULL
    - `role` VARCHAR(50) NULL
    - `title` VARCHAR(255) NOT NULL
    - `message` TEXT NOT NULL
    - `type` VARCHAR(20) DEFAULT 'info'
    - `unread` TINYINT DEFAULT 1
    - `created_at` TIMESTAMP DEFAULT CURRENT_TIMESTAMP
